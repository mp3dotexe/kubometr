# Kubometr

AI-консультант строительного магазина, разработанный на Go.

Kubometr — бэкенд-сервис для строительного магазина: принимает сообщения через мессенджеры (Telegram и MAX Messenger), с помощью AI помогает подбирать материалы и консультирует по вопросам ремонта. История диалогов и пользователи хранятся в PostgreSQL. Приложение контейнеризировано и запускается через Docker Compose.

Бот не подключается к учётной системе магазина: цены и наличие не выдумывает, а передаёт клиента менеджеру. Консультант советует, что брать, и собирает итоговый список к заказу; клиент соглашается кнопкой «Оформить заявку», менеджер получает этот список, звонит и ведёт заявку до выдачи.

## Возможности

- Консультации через Telegram и MAX Messenger (можно включить любой из них или оба сразу)
- Интеграция с AI через OpenRouter (подходит любой OpenAI-совместимый API) с резервными моделями: если одна недоступна или зависла, отвечает следующая
- Индикатор «печатает…» в Telegram и MAX, пока готовится ответ
- Заявки менеджеру: клиент делится телефоном одной кнопкой, в заявку попадает итоговый список консультанта, с которым клиент согласился, и она приходит в чат менеджера в MAX; менеджер ведёт её кнопками «В работе → Готова → Выдана» (или «Отменена»), клиент получает уведомления и видит статус в «Моих заявках»
- Меню кнопок в обоих мессенджерах: консультация, заявка, мои заявки, менеджер, новый диалог, помощь
- История диалогов в PostgreSQL, передаётся модели как полноценный многоходовый диалог
- Автоматическое применение миграций при старте
- Ограничение количества и параллельности AI-запросов
- Ограничение длины сообщений
- Таймауты запросов к AI
- Управление состоянием пользователя
- Разделение транспортного слоя и бизнес-логики (Service Layer, Repository Pattern)
- Юнит-тесты с моками через интерфейсы (dependency injection)
- Docker / Docker Compose для локального запуска (приложение + PostgreSQL)

### Основные компоненты

| Пакет | Назначение |
|--------|------------|
| `telegram` | Работа с Telegram Bot API |
| `max` | MAX Messenger: приём вебхуков, отправка сообщений, подписка |
| `chat` | Общее для мессенджеров: идентификатор чата с платформой, подписи кнопок меню, разбиение длинных сообщений, индикатор «печатает…» |
| `consultation` | Бизнес-логика консультаций |
| `requests` | Заявки менеджеру: итоговый список из диалога, статусы, уведомления |
| `ai` | Клиент AI-провайдера (OpenAI-совместимый API, по умолчанию OpenRouter) |
| `database` | Подключение к PostgreSQL и встроенный мигратор |
| `history` | Хранение истории диалогов |
| `users` | Хранение пользователей |
| `state` | Управление состоянием пользователей |
| `config` | Загрузка конфигурации |
| `logger` | Настройка логирования |
| `app` | Сборка зависимостей и запуск приложения |
| `testdb` | Изолированные схемы PostgreSQL для интеграционных тестов |

Пользователь идентифицируется парой «платформа + ID чата» (`telegram`/`max`), поэтому диалоги из разных мессенджеров никогда не смешиваются, даже если ID совпадут.

## Запуск проекта

### Вариант 1 — через Docker Compose (рекомендуется)

1. Клонировать репозиторий:
```bash
git clone https://github.com/mp3dotexe/kubometr.git
cd kubometr
```

2. Создать `.env` (используйте `.env.example` как шаблон) — переменные `POSTGRES_*` не обязательно совпадать с локальными, Compose поднимает свой контейнер PostgreSQL.

3. Запустить:
```bash
docker compose up --build
```

Приложение будет доступно на `localhost:8080`, PostgreSQL — на `localhost:5433` (проброшен на нестандартный порт хоста, чтобы не конфликтовать с локальной установкой PostgreSQL).

### Вариант 2 — локально, без Docker

1. Клонировать репозиторий и создать `.env`, как выше.

2. Поднять PostgreSQL и создать базу из `POSTGRES_DB`.

3. Запустить:
```bash
go run ./cmd/bot
```

### Миграции

Миграции из `migrations/` встроены в бинарник и применяются автоматически при старте. Версия схемы хранится в таблице `schema_migrations` в том же формате, что у `golang-migrate`, так что при желании на него можно перейти без изменений в базе. Базы, созданные раньше вручную из `000001_init.up.sql`, подхватываются автоматически.

Чтобы добавить миграцию, положите рядом файлы `00000N_name.up.sql` и `00000N_name.down.sql`. Down-миграции автоматически не выполняются, это ручной инструмент для отката.

### Подключение MAX Messenger

1. Задайте в `.env` переменные `MAX_TOKEN` и `MAX_WEBHOOK_SECRET` (любая длинная случайная строка).
2. Сделайте порт `MAX_PORT` доступным снаружи по HTTPS (reverse proxy, например nginx или Caddy), путь вебхука — `/max/webhook`.
3. Укажите публичный адрес в `MAX_WEBHOOK_URL`, и при старте бот сам подпишется на обновления `message_created`, `bot_started` и `message_callback`.

Вебхук сразу отвечает `200 OK`, а ответ консультанта отправляется отдельным запросом через API MAX. В MAX нет кнопки «Консультация», поэтому любое сообщение сразу идёт консультанту. Постоянной клавиатуры в MAX тоже нет, поэтому меню прикреплено к каждому сообщению бота клиенту (в чате менеджера меню нет). Команды: `/start` и `/new` начинают новый диалог и очищают историю, `/requests` — мои заявки, `/manager` — контакты менеджера, `/help` — помощь, `/id` — ID текущего чата.

### Заявки менеджеру

Когда задача ясна, консультант заканчивает ответ блоком «Итого к заказу — задача с размерами:» и списком товаров с количеством. Клиент нажимает «📝 Оформить заявку» и подтверждает отправку номера телефона. В заявку попадает последний такой блок из диалога — ровно то, что клиент видел и с чем согласился, без повторного обращения к AI. Если итога ещё не было, заявка всё равно создаётся, а менеджер видит переписку. Заявка сохраняется в таблицу `requests` и приходит в чат менеджера в MAX: итоговый список, телефон и сообщения клиента.

Менеджер звонит клиенту и ведёт заявку кнопками под сообщением: 🆕 Принята → 🔧 В работе → 📦 Готова → ✅ Выдана. «В работе» можно пропустить, а до выдачи заявку можно перевести в ❌ Отменена. Выданную или отменённую заявку изменить нельзя, повторное нажатие ничего не меняет. При каждом переходе клиент получает уведомление в своём мессенджере («📦 Заявка №12 готова, можно забирать!»), а статус виден в «🧾 Мои заявки».

Чтобы заявки приходили менеджеру:

1. Менеджер пишет боту в MAX `/id` (в личке или в группе, куда добавлен бот) и получает ID чата.
2. Этот ID указывается в `MANAGER_CHAT_ID` (нужен `MAX_TOKEN`), бот перезапускается.

Без `MANAGER_CHAT_ID` заявки только сохраняются в базу, в логе появляется предупреждение. Обычные сообщения в чате менеджера консультанту не отправляются.

Проверка работоспособности (есть, когда включён MAX): `GET /healthz` проверяет доступность PostgreSQL.

### Переменные окружения

| Переменная | Обязательна | По умолчанию | Описание |
|---|---|---|---|
| `BOT_TOKEN` | одна из двух | — | Токен Telegram-бота |
| `MAX_TOKEN` | одна из двух | — | Токен бота MAX |
| `MAX_WEBHOOK_SECRET` | если задан `MAX_TOKEN` | — | Секрет, которым MAX подписывает вебхуки |
| `MAX_WEBHOOK_URL` | нет | — | Публичный URL вебхука для автоподписки |
| `MAX_PORT` | нет | `8080` | Порт HTTP-сервера вебхука |
| `PROXY_URL` | нет | — | Прокси для Telegram (например, `socks5://127.0.0.1:9050`) |
| `OPENROUTER_API_KEY` | да | — | Ключ AI-провайдера |
| `AI_BASE_URL` | нет | `https://openrouter.ai/api/v1` | Адрес OpenAI-совместимого API |
| `AI_MODEL` | нет | 3 бесплатные модели OpenRouter | Модель или список через запятую: при ошибке (лимит, перегрузка, модель снята) запрос уходит к следующей |
| `AI_TIMEOUT` | нет | `30s` | Общий таймаут запроса к AI (на все модели вместе) |
| `AI_MODEL_TIMEOUT` | нет | `20s` | Сколько ждать одну модель, прежде чем перейти к следующей; последняя модель ждёт до конца `AI_TIMEOUT` |
| `AI_RATE_LIMIT` | нет | `3s` | Минимальный интервал между вопросами одного чата |
| `MAX_PROMPT_LENGTH` | нет | `2000` | Максимальная длина вопроса, символов |
| `MAX_CONCURRENT_AI` | нет | `4` | Максимум одновременных запросов к AI |
| `MANAGER_CHAT_ID` | нет | — | ID чата MAX, куда приходят заявки (узнать — командой `/id`); требует `MAX_TOKEN` |
| `MANAGER_CONTACT` | нет | — | Контакты менеджера для кнопки «📞 Менеджер», например `+7 900 000-00-00, пн–сб 9–19` |
| `POSTGRES_HOST` / `POSTGRES_PORT` | нет | `localhost` / `5432` | Адрес PostgreSQL |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | да | — | Доступ к PostgreSQL |

## Тестирование

```bash
go test ./...
```

Интеграционные тесты репозиториев и мигратора работают с настоящим PostgreSQL и без переменной `KUBOMETR_TEST_DATABASE_URL` пропускаются. Каждый тест создаёт себе отдельную временную схему и удаляет её после себя:

```bash
docker run -d --rm --name kubometr-test-pg -e POSTGRES_PASSWORD=test -p 55432:5432 postgres:16-alpine
KUBOMETR_TEST_DATABASE_URL="postgres://postgres:test@localhost:55432/postgres" go test -race ./...
docker stop kubometr-test-pg
```
